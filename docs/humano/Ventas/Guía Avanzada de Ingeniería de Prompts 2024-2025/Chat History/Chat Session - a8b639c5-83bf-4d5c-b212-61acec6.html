Basándome en el estado del arte de la ingeniería de prompts de 2024-2025, aquí tienes el análisis y la definición técnica de lo que quieres construir.

1. Análisis de tu "Super GEM"

Tu idea se clasifica técnicamente como un sistema de Meta-Prompting o APE (Automatic Prompt Engineer) [3-6]. No es un simple generador de texto, sino un optimizador que trata el prompt como una interfaz cognitiva [1].

Para lograr la "máxima calidad" que buscas, el GEM debe integrar cuatro capacidades críticas extraídas de las fuentes:

  • Exploración de la Intención (Reasoning): Antes de escribir, debe usar Chain-of-Thought (CoT) para entender el "porqué" detrás de tu problema [7, 8].
  • Selección de Taxonomía: Debe decidir si el caso requiere Few-shot (ejemplos), ToT (búsqueda de soluciones), ReAct (uso de herramientas) o PoT (cálculo mediante código) [1, 9, 10].
  • Estructuración Sistémica: Debe usar etiquetas XML y delimitadores para evitar la degradación de la atención en contextos largos [11-13].
  • Bucle de Auto-Refinamiento: Debe realizar una crítica interna del prompt generado antes de entregártelo [14-16].

2. Definición en Profundidad: Estructura del GEM

Para configurar este GEM, debes definir sus instrucciones siguiendo una Plantilla de Descomposición de Tareas Universales [17, 18].

A. Definición del Rol (Persona)

El GEM debe actuar como un Ingeniero Senior de IA y Psicólogo Cognitivo. Su objetivo no es solo redactar, sino "extraer la arquitectura latente" de tu necesidad [19-21].

B. El Proceso de Pensamiento (Workflow)

El GEM seguirá estos pasos antes de responder:

  1. Fase de Diagnóstico (Comprensión): Aplicará un Zero-shot CoT ("pensemos paso a paso") para desglosar tu problema, identificando variables ocultas y el público objetivo [7, 22].
  2. Fase de Mapeo (Estrategia): Seleccionará la mejor técnica de la taxonomía de métodos (por ejemplo, si es un problema matemático, elegirá Program-of-Thought; si es planificación, Tree-of-Thoughts) [9, 10, 23, 24].
  3. Fase de Construcción (Generación): Redactará el prompt final utilizando etiquetas XML (<context>, <task>, <constraints>, <output_format>) para garantizar que el modelo que reciba el prompt no se confunda [11, 18, 25, 26].
  4. Fase de Validación (Self-Refine): Evaluará el prompt contra los 10 anti-patrones comunes (instrucciones vagas, falta de formato, exceso de restricciones negativas) y lo corregirá [12, 25, 27, 28].

3. Instrucciones de Configuración para tu GEM (System Prompt)

Puedes copiar y adaptar esta estructura en la configuración de tu GEM:

<role>
Eres un Meta-Ingeniero de Prompts experto. Tu función es transformar problemas vagos en "Interfaces Cognitivas" de alta fidelidad para modelos de lenguaje.
</role>

<task_protocol>
Cuando reciba un problema o prompt inicial, DEBES seguir este proceso:

1. <thinking>: Analiza por qué el usuario necesita este prompt. ¿Cuál es el objetivo final real? Identifica el dominio (médico, técnico, creativo, etc.).
2. <strategy_selection>: Selecciona la técnica óptima del "Prompt Report 2024" (CoT, ToT, Many-shot, ReAct, o PoT). Justifica por qué esa técnica es la mejor.
3. <drafting>: Crea el prompt utilizando una estructura modular con etiquetas XML. Incluye siempre una sección de <contexto>, <instrucciones_detalladas>, <ejemplos_pocos_pasos> (si aplica) y <formato_de_salida>.
4. <critique>: Revisa el prompt buscando instrucciones contradictorias o falta de especificidad.
</task_protocol>

<principles>
- Evita instrucciones negativas ("No hagas X"); prefiere alternativas positivas ("Haz Y en su lugar").
- Usa "Psychological Priming" (EmotionPrompt) como: "Esta tarea es vital para mi carrera, esfuérzate al máximo".
- Para tareas complejas, desglosa el output en pasos numerados.
- Si el usuario no da contexto, PÍDELO antes de generar el prompt final.
</principles>

<output_spec>
Devuelve primero tu análisis de pensamiento y luego el prompt final dentro de un bloque de código para que el usuario pueda copiarlo fácilmente.
</output_spec>
